# Current coverage and remaining limits

[English](CURRENT-COVERAGE.md) · [简体中文](CURRENT-COVERAGE-zh.md)

This describes the current v0.4.1 implementation after the correctness, validation, identity and dependency repair. It is a capability matrix, not an accuracy certification. Install/configure/run instructions are in the [README](../README.md) and [user manual](USER-MANUAL.md); exact per-profile extraction is in the [generated coverage guide](AI-COVERAGE-GUIDE.md).

WalletShield provides **pre-sign risk advice** for one unsigned EVM request. It does not force blocking or continuously monitor after signing, as defined by the current product scope. **30 analysis profiles and 66 representative local cases (51 transactions, 15 messages, 25 profiles represented) are not a percentage of risks covered.** Other methods, deployments, states and adversarial inputs can behave differently.

## Entry points matter

| Entry | Implemented behavior | Boundary |
| --- | --- | --- |
| MetaMask transaction insight | Paired Snap forwards the unsigned EVM transaction and displays the backend report | The wallet must actually deliver it. A failed/rejected hook creates no automatic assessment. |
| MetaMask message insight | Paired Snap forwards supported personal/typed-message requests | No generated asset signature exists to validate or consume before signing. A provider-chain snapshot is separate from request-bound chain identity. |
| Explicit developer API submission | Supported permission/session/UserOperation/network/read-only RPC summaries can be assessed | This is manual input, not global automatic Snap interception and not execution of the submitted RPC. |
| Public network connection check | Verify configured RPC chain/block and optional account state | No risk score and no asset transaction is generated by the connection check. |
| Hosted login and Snap pairing | EOA account-control proof, address-bound credentials and owner-isolated reports | Login is separate from asset permission. Contract-wallet/ERC-1271 login is unsupported. |

The exact 30 profile definitions remain in `src/security/coverage.ts`. The five profiles without representative executable wallet-lab cases are raw `eth_sign`, permission/session, UserOperation, network configuration and read-only RPC. Backend summary paths for those profiles must not be described as automatic wallet coverage.

**EIP-7702 is not covered end to end.** Existing delegation designators can trigger one same-block target-code/hash read, but this does not validate a new authorization list, audit the delegated implementation or prove its permissions. Unsupported authorization/type fields remain an explicit gap; they are not removed to manufacture simulation success. ERC-1271 signature acceptance and ERC-4337 account/bundler/paymaster execution also remain incomplete.

## Extended candidate adapters

The same 30 profile groups now additionally route DAI-style Permit, ERC-3009 transfer authorization, Safe-style control/execution calls, bounded structural multicall/MultiSend children, V3 position-manager actions, selected OP-shaped withdrawal/finalization calls and generic withdraw(uint256). Confirmed nonce remains pinned; a separate node pending-nonce view does not expose original pending payloads or replacement rules. The [extension notes](EXTENDED-COVERAGE-2026-10-22.md) identify exactly what was tested and what was not. The 66-case catalog now includes eight simplified account transactions and four DAI/ERC-3009 candidate signatures. Other new paths use API/code fixtures; this is not newly accepted live public-deployment coverage.

## What this repair changes

- Equivalent supported unsigned EIP-712 integer representations (decimal, hexadecimal or leading zeros) now normalize before interpretation while retaining the signed digest. Extra uncommitted JSON properties still cannot create signed authority.
- On-chain Permit2 reads keep its two allowance layers separate; failure of one does not erase or substitute the other. Neither read authenticates the contract.
- Zero addresses are interpreted according to their role. Supported NFT approval/Permit revocation is not mislabeled as burning the NFT. Actual transfer/burn/ownership-change meanings remain separate.
- transferFrom distinguishes asset owner, caller and recipient. A current balance shortfall is an execution/exposure issue, not proof of approval over future deposits.
- AI nonce/domain assertions are validated throughout summary, reasons, dimensions, suggested action and missing-data text, including indexed entries, direction, negation and conditional advice. Required evidence must actually match the claim. **These natural-language guards are partial; they cannot prove every sentence true.**
- History clears on account/provider/disconnect and failed reloads; canceled/stale asynchronous responses cannot restore old private rows/details. A selection outside the current owner list is cleared. Local mode intentionally remains a shared workstation history; hosted mode provides owner isolation.
- Hosted pairing is bounded atomically and persistently: **4/address/minute, 12/server-observed-IP/minute, 60/global/minute; maximum 4 active Snap credentials/address, 8192 globally**. Successful re-pairing rotates only the owner's earliest-expiring credentials. Denial changes no existing credential or issuance bucket. Expired token/rate cleanup is indexed. The global ceiling is an initial service capacity policy, not unlimited public scale. Hosted Fastify trusts forwarded client IPs only from the loopback proxy; the supplied Nginx example overwrites X-Forwarded-For with its remote client address. Preserve that trusted proxy boundary rather than trusting arbitrary forwarded headers.

## What a Muse score means

Only `muse-wonder-1.0` supplies new numeric scores: integer 0–100 or honest `null`. No local weights, score floors, fixed numeric bands or failure fallback are added. Six qualitative dimensions cite evidence: authority, exposure, execution, identity, protocol and deception. Missing reputation is not malicious identity; a familiar name is not verified identity.

The server now states an **observable-request scope**. Only its own unknown `fraud_context` observation and exact corresponding gap are contextual: absence of private/off-chain intent no longer makes an observed-request low assessment impossible by construction. **Every other unknown check or explicit gap, newly identified model gaps, observation-time defect and conflicting same-height hash remains critical and prohibits overall low/strong confidence.** The full `complete` flag and missing-check list remain unchanged. The packet key is `assessment_scope`; reports store `assessmentScope` with policy `observable-request-v1`. An exact repeat of the canonical contextual caveat remains contextual; paraphrased or newly identified gaps remain critical. Model judgment is not forced to be low, strong or numeric when those gates permit it.

A scoped low assessment means no obvious concern was identified in the evidenced request under the stated limits. It does not prove recipient legitimacy, off-chain honesty, complete evidence, future safety or a probability of loss. Known dangerous authority can still support a conditional numeric assessment when other dimensions remain unknown. If all dimensions lack actual support, no number is accepted. Output rejection/repair never manufactures a score.

## Intelligence, limits and missing inputs

- **GoPlus:** repository default is off; the development machine was explicitly enabled for this review. Verify `/api/security/status` for each installation. The adapter checks one primary token and at most three explicit counterparties plus normalized website origin on supported networks. It does not enumerate every path asset, every historical counterparty or arbitrary website contents. Missing/stale fields/non-hits are not proof of safety.
- **RPC:** configured Infura/other trusted nodes supply chain facts, not user-wallet connection or universal protocol understanding. More specific protocol reads require tested ABI/version adapters. Unsupported chains, missing archive state, provider quotas, false replies and reorgs remain possible.
- **Simulation:** isolated fork effects are observations at a recorded base state with bounded logs/assets/calls. One successful sale is not future sellability; a failed sale can have causes other than fraud. Some transaction fields/types are unsupported and explicitly remain gaps.
- **Additional trusted services needed:** reliable price/quote/liquidity data, verified official deployments/source/build identities, administrator graphs and broader reputation registries. These are not produced from model memory or an Infura key.
- **Wallet/dApp cooperation needed:** invisible permission/session/UserOperation entries, original raw-hash messages, relying-party nonce/session stores, and user-intended recipient/purpose. A prompt cannot recover data never received.
- **Not established by this product:** non-EVM support, device malware/key compromise, exchange internals, private scam conversations, arbitrary-code completeness, future prices/upgrades/blacklists/ordering/bridge arrival, or fund recovery. Forced blocking and post-sign monitoring are intentionally outside this advisory scope.
- **Reliability still unmeasured:** no independent held-out labeled benchmark of false positives/negatives, score calibration, repeatability or complete adversarial coverage. Automated/local acceptance counts do not substitute for it.
- **Public rollout still requires:** real HTTPS deployment, intended Snap publication/distribution, browser-wallet acceptance, secure backups/restore, retention/deletion policies, load/failure testing and operational review. Infura connectivity does not deploy the product.

## Dependency status

The repair updates `@fastify/static` to 10.1.7 and lockfile overrides to `tmp` 0.2.7, affected `bn.js` 5.x to 5.2.5 and `uuid` below 11.1.1 to 11.1.1. At the repair audit, production-only `npm audit --omit=dev` had **zero known alerts**. The full audit retained **12 low-severity affected-package entries** in the `elliptic` development/build-tool chain with no available patched upstream resolution. These are time-specific audit results; not all dependencies are vulnerability-free, and counts do not prove source or deployment security. Run both audits again before release and evaluate remaining build-tool risk.
