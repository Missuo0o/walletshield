# Extended candidate coverage — 2026-10-22

This v0.4.1 extension adds bounded adapters within the existing **30 analysis profiles**. It does not turn those profiles into complete protocol integrations, and it does not change the policy that only Muse supplies new numeric scores. Read the [current matrix](CURRENT-COVERAGE.md), [中文范围对照](CURRENT-COVERAGE-zh.md), [user manual](USER-MANUAL.md) and [field guide](AI-COVERAGE-GUIDE.md) together with the actual report.

Current checks use the wallet-supplied unsigned request, source origin/network metadata and successfully collected RPC, intelligence and simulation evidence. Muse assesses observable request signals, including supported source/message/request inconsistencies. Chain/provider/execution context means technical observations. Historical reports and acceptance artifacts retain their original recorded data.


## Request and evidence flow

MetaMask must deliver the unsigned transaction/message to the paired Snap. The backend validates it, decodes an exact supported shape, selects applicable collectors and supplies observations and explicit unknowns to Muse. The model does not browse the protocols or run these tools itself. The webpage initiates explicitly selected tests and displays reports; hosted EOA login/pairing remains separate from asset authorization. Manual permission/session/UserOperation/RPC summaries still have no universal automatic Snap hook.

Canonical decoding rejects unsupported/trailing/malformed encodings rather than silently accepting them as the referenced protocol. Every RPC collector uses only the server-configured trusted endpoint. An address, readable interface or familiar selector is not a verified deployment identity. Full unsigned requests remain in backend storage; structural batch summaries omit raw child calldata and signature bytes from their evidence. No request private key, seed phrase or generated asset signature is needed.

## New paths and exact interpretation

| Path and tools | Added extraction / observation | Limits that remain visible to Muse |
| --- | --- | --- |
| DAI-style Permit — `decode.ts`, `signatures.ts`, `assets.ts` | Exact committed `holder`, `spender`, `nonce`, `expiry`, `allowed`; derive maximum uint256 allowance for true or zero for false; supported holder nonce, DOMAIN_SEPARATOR, expiry/block-time and same-token conditional balance exposure | Derived amount is reference semantics, not an additional signed amount. Reference expiry zero means no submission deadline, not automatic expiry or allowance lifetime. Matching shape/state does not authenticate the token or generated signature; consumption is not executed. |
| ERC-3009 — the same signature/asset collectors | Exact TransferWithAuthorization/ReceiveWithAuthorization payer/from, recipient/to, value, validAfter/validBefore and bytes32 nonce; `authorizationState(authorizer, nonce)` and domain comparison | Single committed transfer, **not standing allowance**. Window is strictly open: after < block time < before. A used state can mean used or canceled. Receive form conditionally requires future caller=recipient; no future caller/signature/consumption is proved. Sequential Permit nonce or allowance cannot substitute for authorization state. |
| Safe-style account controls — `account-operations.ts`, `account-evidence.ts` | Exact add/remove/swap owner/threshold, enable/disable module, set/remove guard/fallback, approveHash and execution wrapper parameters; fixed-block owners (up to 64 retained), threshold, selected module and code; compare requested/observed threshold | No authenticated Safe version, full module/guard/fallback graph, linked-list/policy validation, owner contract signature acceptance or code audit. Guard removal can weaken protection. `getGuard` is internal; no fictional public getter is queried. approveHash has no known action preimage. |
| Safe execution and batch structure — `account-operations.ts`, `batch-evidence.ts` | Canonical multicall(bytes[]), multicall(uint256,bytes[]), execTransaction and packed MultiSend; candidate children, CALL/DELEGATECALL, encoded values/targets/selectors, bounded recognized parameters, refund quantities and signature sizes | Depth 3, global 32 children, 16384 bytes/body, 32768 recursively inspected bytes. Explicit unknowns cover malformed/unsupported/truncated input and unverified child sender/owner/storage context. DELEGATECALL encoded value is not a separate native transfer. No signature or execution proof follows from structure. |
| V3 concentrated liquidity — `protocol-operations.ts`, `position-evidence.ts` | Exact mint/increaseLiquidity/decreaseLiquidity/collect tuples; tick/fee, token ID, desired/min/max quantities and protocol-liquidity units. Existing IDs read positions, NFT ownership/approval/operator, manager code and token units/caller balances at a fixed block | No pool/manager authenticity, current price/tick/liquidity validation, quote, NFT/LP valuation, complete exit/fee economics or future proceeds. Mint has no existing ID. Collection caps and reported owed quantities are not guaranteed proceeds. |
| Additional OP-shaped bridge stages — `protocol-operations.ts` | Selected withdraw/withdrawTo, bridgeETH/bridgeERC20 and finalizeBridgeETH/ERC20 alongside existing deposit/to forms; stage, local/remote token, claimed sender/recipient, amount/value, gas and extraData size | Parameter decoding only. No portal/messenger/proof, destination deployment, message status/finality/arrival, validator/custody or future relay verification. Finalize-shaped calldata is not validated completion. |
| Generic withdrawal — `protocol-operations.ts` | `withdraw(uint256)` becomes `withdrawal`, with `amountKind=unverified_protocol_units` and `redeemabilityVerified=false` | Not automatically staking, WETH or native redemption. Meaning/units/rate, restrictions, identity, solvency and actual asset receipt remain unverified. |
| Pending nonce context — `providers.ts` | Confirmed nonce retains pinned block provenance; `transaction_pending_nonce` separately records one node's unpinned pending count and whether a supplied nonce overlaps that observed range | Pending can omit private/remote transactions or conflict with the confirmed snapshot. No original transaction payload, cancellation intent, replacement-fee policy or inclusion guarantee is available. A candidate overlap is not proof of a safe replacement. |

Conditional exposure keeps authorization types separate. Permit2 transfer authorizations are single-nonce transfer caps rather than standing allowances. ERC-3009 commits an exact amount: if the same-token snapshot balance is below that amount, `balanceCoversDeclaredAmount=false` is retained and no smaller partial-transfer bound is reported. Allowance/cap paths can use a conditional minimum of the relevant cap, balance and underlying Permit2 allowance where available. None is observed consumption or future loss. An empty-data DELEGATECALL remains delegated code execution, not a native transfer; its encoded value is not a separate native payment.

Safe's execution selector has signatures as an argument because it can submit a previously authorized account transaction. That is different from asking the current EOA wallet to sign a fresh Safe typed message. Neither path supplies a complete ERC-4337 account/bundler/paymaster implementation or full ERC-1271 signature validation.

These are offline or owned-local-state regressions with synthetic fixtures, not a new paid-model accuracy evaluation. Final suite/lab results are recorded separately in the current verification artifact; a catalog entry is not proof of manual MetaMask/Snap delivery. Local fixture signatures can deliberately lack a matching live-token getter/consumer so unavailable nonce/domain/authorization evidence must remain unknown. Preparing assets does not authorize a router/module, create positions or simulate a real official protocol for you.

## Local wallet catalog

The catalog is now **66 cases: 51 transactions and 15 signatures**, still representing **25 of 30 profiles**. Eight optional simplified account transactions and four DAI/ERC-3009 candidate signatures were added. V3 position and extra bridge-stage adapters are backed by code/API tests, not equivalent official-protocol live-wallet scenarios.

On an existing lab, `npm run deploy:lab` explicitly adds optional LabAccount without replacing prior fixture addresses, then asset preparation resets its tester. This is owner-direct, not multisig enforcement: any listed owner can call regardless of threshold; modules/guard/fallback are flags; only CALL with empty signatures and zero refunds is accepted, with DELEGATECALL deliberately rejected. The candidate signature tests use LAB-USD's domain but no DAI/ERC-3009 consumer or ERC-3009 authorizationState getter exists. Missing evidence remains unknown. A successful local case does not validate a real deployment or browser Snap delivery.

## Remaining gaps

- Permit2 common allowance/transfer paths remain bounded; witness and custom variants, full orders/fulfillment/cancellation and all authority forms are incomplete.
- EIP-7702 only observes recognized existing delegation designators and a bounded target-code read. New authorization-list correctness, implementation authority and end-to-end execution remain incomplete.
- ERC-4337 and ERC-1271 are not solved by Safe-shaped methods. Contract-wallet service login remains unsupported. Permission/session/network/read-only RPC interception still needs a wallet/dApp integration.
- Source/deployment identity, trusted prices/quotes/oracles, complete authority graphs, arbitrary code/hidden assets, bridge proofs/arrival and future sellability remain unresolved where stated.
- GoPlus remains bounded to one primary token, three explicit counterparties and normalized origin on supported networks; it is not full asset enumeration, price/identity verification or universal honeypot detection.
- Independent held-out benign/malicious evaluation, score stability/calibration and broad adversarial measurement are still needed. Muse's number is advisory evidence assessment, not loss probability.
- HTTPS deployment, intended Snap distribution, actual browser-wallet acceptance, data lifecycle, backups/restore and operational load/failure review remain separate release work. Forced blocking and continuous post-sign monitoring are intentionally outside scope.

## Primary specifications and source references

These references justify the candidate interfaces, not the identity of a contract at any user-supplied address:

- [ERC-3009 specification](https://eips.ethereum.org/EIPS/eip-3009): authorizer-scoped bytes32 authorization, open time window, receive-caller restriction and one-time transfer semantics.
- [DAI reference implementation](https://github.com/sky-ecosystem/dss/blob/master/src/dai.sol): `allowed` mapping, holder nonce and reference submission expiry semantics.
- [Safe execution interface](https://docs.safe.global/reference-smart-account/transactions/execTransaction), [OwnerManager](https://github.com/safe-fndn/safe-smart-account/blob/main/contracts/base/OwnerManager.sol), [ModuleManager](https://github.com/safe-fndn/safe-smart-account/blob/main/contracts/base/ModuleManager.sol), [GuardManager](https://github.com/safe-fndn/safe-smart-account/blob/main/contracts/base/GuardManager.sol), [FallbackManager](https://github.com/safe-fndn/safe-smart-account/blob/main/contracts/base/FallbackManager.sol) and [MultiSend](https://github.com/safe-fndn/safe-smart-account/blob/main/contracts/libraries/MultiSend.sol): supported owner/module/guard/fallback/execution and packed batch shapes.
- [Uniswap V3 position-manager interface](https://github.com/Uniswap/v3-periphery/blob/main/contracts/interfaces/INonfungiblePositionManager.sol): mint/increase/decrease/collect tuples, positions and distinct liquidity/owed-token units.
- [OP StandardBridge](https://github.com/ethereum-optimism/optimism/blob/develop/packages/contracts-bedrock/src/universal/StandardBridge.sol) and [L2StandardBridge](https://github.com/ethereum-optimism/optimism/blob/develop/packages/contracts-bedrock/src/L2/L2StandardBridge.sol): selected stage parameters, without claiming portal or cross-domain proof verification.
- [Ethereum JSON-RPC documentation](https://ethereum.org/developers/docs/apis/json-rpc/): node state and the `pending` block parameter; pending observations are not a global transaction-intent oracle.
