# WalletShield 0.2：历史能力说明

**当前已升级 0.3，新增副本模拟、部分连续买卖、签名 nonce / domain、监控和配对。请先阅读 [当前交付说明](RELEASE-v03.md)。下文保留为 0.2 的历史边界，不作为当前验收结论。**

## 当前结论

这是覆盖更多 EVM 请求的签前检查版本，已完成代码和离线验证。不是“所有钱包安全问题都已解决”。AI 用已有证据给意见，不会自动获得链上数据，也不能只凭一段交易判断投资平台是否诈骗。

## 操作覆盖表

| 操作 | 当前实现 | 仍缺少的验证 / 限制 |
|---|---|---|
| ETH 等原生币转账 | 解析收款方、金额，读取余额 / 目标代码，基础 eth_call | 地址真实身份、资金用途、完整内部调用和资产变化 |
| ERC-20 transfer / transferFrom | 解析地址与数量，读取常用代币接口 | 非标准代币、转账税、最终到账资产差异 |
| ERC-20 approve / 撤销 | 区分额度、超余额、极高权限，查询既有 allowance | 名称和接口不能证明代币或 spender 可信 |
| NFT approve | 区分 tokenId 与金额；NFT #0 不能当撤销 | 非标准 NFT / 恶意接口可能欺骗分类 |
| NFT setApprovalForAll | 提示集合全量 operator 权限与撤销 | operator 的所有后续使用与当前 NFT 权属未完整验证 |
| ERC-721 / ERC-1155 转移与批量转移 | 常见 safeTransferFrom / safeBatchTransferFrom 严格解码 | 回调、内部转移和全部资产结果未模拟 |
| 常见 V2 兑换 | 解析路径、输入量、最小输出、收款方、期限；可查输出代币情报 | V3 / Universal Router / 自定义路由、完整价格与滑点、买卖连续模拟 |
| Permit / Permit2 | 常见签名候选与链上额度方法；展示 token、spender、额度、期限 / nonce 等已解析字段 | 完整类型语义、nonce 有效性、全部 token 与最终消费场景未验证 |
| personal_sign / 钱包登录 | 提取可读预览、登录域名 / 地址 / 网络 / 期限，检测明显不一致 | 普通消息用途、重放、业务授权与消息真实性未完整验证 |
| 结构化签名 / NFT 挂单 | 常见 Permit / Permit2、订单候选；未知结构显式提示 | 不把 primaryType 名称当可信语义；没有完整协议订单模拟 |
| eth_sign | 手动检查时显示原始签名风险 | 自动 Snap 入口不保证提供此方法 |
| 批量调用 / 桥接 / 借贷 / 质押 / 流动性 / 部署 | 未识别或复杂请求保留不完整标记，不假装已检查通过 | ABI、协议语义、调用树、资产差异、跨链结果 |
| 连接权限 / 切链 / 会话密钥 / 智能账户 | 手动输入可标示权限 / 委托风险，通常无法完整理解 | 没有自动拦截这些 RPC、权限生命周期与 UserOperation 仿真 |
| EIP-7702 | 目标代码带委托前缀时提示 | 不分析所有授权列表、委托逻辑与会话策略 |
| 助记词 / 设备 / 交易所 / BTC / Solana | 当前未覆盖 | 需要其他产品入口与专门实现 |
| 签后监控 / 自动撤销 / 强制阻止 | 当前未实现；旧授权测试有请求回报和回执核对 | Snap 见解不是全局防火墙；不能撤回已发生损失 |

“有解析器”和“能证明安全”是两件事。未识别调用、缺少网络、情报失败或缺少模拟均保留未知。表中自动入口仍需用户安装 0.2 Snap 并完成 Flask 实机验收。

## 哪些数据会进入模型

仅启用 AI 且配置密钥后，后端发送：

- 请求网络（消息入口未知为 0）、网站 origin（剔除路径 / 参数 / 凭据）、用户填写的用途。
- 公开发送地址、目标地址、原生币 wei 数量、selector 和 calldata 长度；不发送整段 calldata。
- 已解出的转账金额、代币、spender / operator、NFT ID、兑换路径、期限、消息预览或结构化签名的已选字段。
- 链上查询的区块、余额、目标代码状态、代币接口、既有授权，以及可选情报源的白名单标记。
- 每项检查的来源、时间、状态、缺失项；新评分不包含规则数字或下限。

不主动读取或发送助记词、私钥、已生成的签名、供应商密钥、整个钱包历史或整个数据库。签名前的原始请求保存在本机 SQLite；用户自行填写的用途与消息可能包含个人信息，因此启用 AI 前应确认适合传给 OpenAI。可用 `/api/security/records/:id/evidence` 查看白名单输入。

OpenAI 使用 Responses API、严格 JSON schema、`store:false`，这不等于零数据留存承诺。GoPlus 仅在单独启用后收到目标公开地址、代币地址、网络和网站 origin；供应商覆盖范围与条款需在上线前确认。

## 分数的含义

- AI 未运行、失败或被关闭：无数字评分；保留规则信号与缺失项。
- 新分数完全由 Muse 按本次证据独立给出，无规则预设分数、最低分、加分表或固定权重；历史规则分数不重写。
- 模型输出 0–100 风险指标、理由与证据 ID、缺失数据、建议操作。不存在的证据、缺数据却称低风险、无依据的 honeypot 结论会被拒绝；模型可返回 null 而不编造数字。
- 这些结构约束不能证明模型解释在语义上绝对正确。上线前仍须用已标注案例评测误报、漏报、分数稳定性、成本和延迟。
- 检查状态与用户签署 / 取消 / 链上执行状态分别处理；新综合报告只描述签前检查。

## Honeypot 与杀猪盘

当前提供可选代币情报适配：honeypot 标记、不能全部卖出、买卖税、暂停 / 黑名单 / 可改税 / 管理员改余额 / 增发等已有字段。查询失败、空字段及情报未启用保留未知；合约调用成功不等于能卖出。演示 honeypot 是明确标注的预设数据。

可靠的下一阶段检测需要：在固定链上状态，按实际路由连续模拟买入 → 需要的授权 → 卖出；检查到账数量、税与内部转移，并结合流动性、源码 / 代理实现和管理员可变权限。当前没有完成这套模拟，不得声称已提供真实 honeypot 保证。

杀猪盘可能使用正常 ETH / USDT 和正常收款地址。交易本身不足以证明平台、投资承诺或沟通者的身份。来源网站情报仅解决已知钓鱼部分；仍需产品中取得用户目的、平台信息及必要上下文，并在隐私约束下分析。AI 不应因“没命中黑名单”就给安全承诺。

## 后续实施顺序

1. 用户手动重新加载 Snap 0.2，验证原生币、代币、NFT 和 personal_sign / Permit 的真实提示与失败分支。
2. 在用户准备配置密钥后，单次真实 OpenAI 联调；核对输入包、真实响应、延迟、token 用量及故障回退。
3. 选择一个 EVM 网络、有限的已知路由和资产，补完整资产模拟与连续买卖检测，再用已标注历史案例评测。
4. 接入真实地址 / 域名情报，验证网络支持、更新频率、失败模式和用户可理解的解释。
5. 验证权限 / 智能账户的可接入入口，再逐步扩展协议与链；另行建设签后监控及上线安全控制。
